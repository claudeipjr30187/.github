<p>画成树形之后，排查就不用靠猜。根节点是「这条住宅节点不好用」，往下一层分成三支：慢、丢、断。慢再分成首跳慢、末跳慢、DNS慢；丢再分成持续丢、突发丢、定向丢；断再分成整段断、单IP断、被限流。每一支都对应具体的验证命令和判定阈值。最后讲怎么把三个指标做成连续观察，以及怎么把这棵树写进值班手册，让半夜出问题的人不用问人也能处理。</p>
<h2>一、症状定义：先分清三种「不好用」</h2>
<p>「不好用」是最没用的描述。先归到三类：打开页面要等很久（慢）、页面加载到一半失败（丢）、完全连不上（断）。三类的原因链完全不同，混在一起排查只会浪费时间。</p>
<h3>先记三个数再动手</h3>
<p>动手前先记下：问题发生的时间、受影响的IP、以及同一时间其他IP是否正常。这三个数决定了后面往哪一支走。没有这三个数，任何排查都是猜测。</p>
<h2>二、第一分支：延迟高，往下三种可能</h2>
<p>用 mtr -rwzc 100 目标域名，看每一跳的平均延迟。延迟高不是结论，要看高在哪一跳。</p>
<h3>首跳就高：本地接入问题</h3>
<p>第1、2跳延迟超过 20ms，通常是本地网络或代理客户端的转发开销。检查是否开了双重代理、是否走了本机的全局模式、以及客户端所在的机器是否在跑其它占带宽的任务。</p>
<h3>中间某跳高而后面的跳回落：正常现象</h3>
<p>这是路由器的 ICMP 限速，不代表真实转发慢。判断方法是看后续跳是否回落，如果回落到基线，直接忽略这一跳。</p>
<h3>末跳持续高：出口侧问题</h3>
<p>末跳延迟长期高于 250ms 且抖动大于 50ms，说明出口到目标之间链路拥塞或绕行。用 mtr 看是否经过三个以上国家，绕行往往伴随高延迟。</p>

<h2>三、第二分支：丢包，从哪一跳开始算</h2>
<p>丢包的判定必须看「从哪一跳开始丢、后面是否延续」。中间跳零星丢包而后面的跳不丢，是正常的路由器保护机制。</p>
<h3>持续丢包</h3>
<p>从第 N 跳开始每跳都有相近比例的丢包，说明第 N 跳之后的链路有问题。这种情况换IP比调参有效。</p>
<h3>突发丢包</h3>
<p>只在特定时段出现，比如每晚 20:00 到 23:00。这是民用宽带的典型特征，接入网在高峰期争抢。可以通过把重要任务挪到非高峰时段缓解，不必换线路。</p>
<h3>定向丢包</h3>
<p>只对某个目标丢、其他目标正常。用 ping 分别测三个不同目标，如果只有一个丢，问题在目标侧或中间某段对该目标的策略，不在你的节点。</p>

<h2>四、第三分支：可用率低，多数不是线路问题</h2>
<p>可用率是结果指标，不是原因。统计一个月的数据后，经常发现「不可用」的时段集中在少数几个时间点，进一步查是本地出口IP变了导致鉴权失败，跟住宅节点无关。</p>
<h3>先区分探测失败与业务失败</h3>
<p>探测失败指健康检查请求不通；业务失败指业务请求返回错误。两者要分开统计。很多团队把 401、403 也算成线路不可用，导致误判。</p>
<h3>按错误码分组看</h3>
<p>把日志按状态码聚合：连接超时归一类、407/403 鉴权归一类、5xx 归一类、429 归一类。哪一类占比最高就先修哪一类。经验上，鉴权类问题在自建代理环境里占的比例比想象中高。</p>
<h2>五、把三个指标做成连续观察</h2>
<p>单次测量没有意义，连续观察才有。建议采集频率与观察周期按下表设置。</p>

<h2>六、故障树怎么落到值班手册</h2>
<p>把上面三支写成「如果……则执行……否则……」的短句，每条不超过两行，附上命令。值班的人照着敲就行，不需要理解原理。</p>
<p>手册里要写清升级路径：什么情况下自己处理，什么情况下找服务商，什么情况下直接换IP。经验值是——单IP问题自己换，整段问题找服务商，跨城市跳变直接换并留证据。</p>
<p>另外留一栏「事后记录」，写清发生时间、影响范围、处置动作、根因。三个月后回看这一栏，能发现大部分故障其实是同一类，那时候再改架构才有依据。</p>
<h2>常见问答</h2>
<h3>mtr 中间跳丢包但末跳不丢，算故障吗？</h3>
<p>答：不算。多数路由器对 ICMP 做限速，中间跳的丢包率不代表转发质量。判断依据是末跳的丢包和业务请求的实际失败率，两者都正常就不用处理。</p>
<h3>可用率 99% 是什么水平？</h3>
<p>答：按每 30 天算，99% 意味着累计约 7 小时不可用。对住宅线路来说这是常见区间，机房线路通常更高。业务能否接受，取决于不可用是否落在你的关键时段。</p>
<h3>连续观察要跑多久才够？</h3>
<p>答：至少 14 天，且要覆盖两个完整周末。住宅线路的负载有明显的时间规律，只测工作日白天会得出偏乐观的结论。</p>
<h3>出口IP变了但还能用，需要处理吗？</h3>
<p>答：需要。出口变化会影响账号的登录地记录，即使当下能用，也可能在后续触发验证。建议先锁定原出口，查清是运营商动态分配还是服务商调度。</p>
<h2>合规提示</h2>
<p>本文的故障排查方法适用于自有节点与自有账号的运维场景。使用 mtr、ping 等工具时，应仅针对自己有权测试的目标，避免对第三方网络造成干扰。</p>
<p>日志中可能包含账号、IP、访问记录等信息，应按内部数据管理规范保存与脱敏，避免泄露个人信息或商业数据。</p>
<p>文中阈值与周期为经验参考值，实际应根据业务重要性和线路特性调整，并以长期监测数据为准。</p>
